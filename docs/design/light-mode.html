Light mode · three variants

The app is dark-only today: tokens.css defines one :root palette, and nothing in web/src handles [data-theme] or prefers-color-scheme. Each variant below uses the app's own stylesheets and markup with a different token set applied, so what you see is what a token swap would actually produce. The contrast numbers are calculated live from each variant's tokens.

A · Paper B · Dark chrome C · Cool slate What every variant needs

Recommendation: A · Paper

It is the existing grey ladder inverted, so it keeps the rule tokens.css was built on (neutral greys, one accent, colour only for meaning), and it ships as a single [data-theme="light"] token block with no per-region rules. The pale selection keeps the red and amber of Blocked and Waiting readable in the selected row. C's solid selection turns them white.

Cost: app.css hardcodes about ten colours that have to become tokens first: --sel-fg, string and number value colours, treemap ink, shadows, scrim, and the literals in debug.css. tokens.ts needs a light mirror for the canvas, the graph and report export. Red and amber had to be darkened to stay AA on the pale selection. The host also has to switch the native caption buttons to light, which B avoids.

A · Paper

recommended
  • White content area, light grey chrome (--bg-2 #f3f3f3). The step order is reversed so that higher steps are darker.
  • Pale blue selection with dark text and a 2px accent edge. State colours stay visible in the selected row.
  • Red, amber and green are darkened to meet AA on both white and the selection colour.
  • Closest to the restyle's principle. There is the least to argue about.

B · Dark chrome, light canvas

  • Titlebar, rail and status bar keep today's dark tokens. Only the working area turns light, using the same content tokens as A.
  • This puts a strong frame around the data and makes the active view easy to find. The native caption buttons can stay dark, so the host needs no change.
  • Two palettes are live at the same time, so every component used in the chrome (.btn, .kbd, .search, focus ring) has to work in both.
  • The dark and light boundary is a strong edge, and it competes with the inspector's left border.

C · Cool slate

  • The surfaces and lines have a slight blue-grey tint, which feels cooler and more like a typical tool than A.
  • Selection is solid accent blue with white text, so today's .trow.sel > * { color: #fff } rule keeps working unchanged.
  • Selection is the strongest thing on screen. The cost is that Blocked and Waiting lose their colour in the selected row, as they already do in dark mode.
  • The tint takes the greys slightly away from "colour only for meaning".

What every variant needs

  • A theme mechanism: :root[data-theme="light"] overriding the tokens, defaulting to prefers-color-scheme with a manual override that is saved. Add color-scheme so scrollbars and form controls follow the theme.
  • New tokens for colours app.css hardcodes: --sel-fg (#fff at the .trow.sel and .bar-row.sel rules), --val-str / --val-num (#a7f3d0 / #fcd34d), --tm-fg (treemap #fff), --shadow (#0009/#0008/#0006), --scrim (#05070999).
  • debug.css uses its own dark literals (#536376, #e6ac55, #ffa6a6, #ffffff18). These need to become tokens or a scoped light block.
  • tokens.ts mirrors every token for canvas, React Flow and report export. It needs a light set, chosen at runtime.
  • Native caption buttons over .wc are drawn by the host (shown here as stand-in glyphs). A and C need the host to switch them to light.
  • Not mocked: the treemap fills and lock-graph edge colours come from tokens.ts and need their own pass.
