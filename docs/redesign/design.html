Dump Debugger · Redesign
Draft · 2026-11-11
Vision

Plain answers first, every byte one click away.

Dump Debugger becomes the tool an on-call developer reaches for at 2 a.m. with a hang dump and no WinDbg muscle memory. It opens with a verdict in plain English, tells you what to do next, and backs every claim with evidence you can click through: thread, lock, object, and the path that keeps it alive.

What's wrong today

01

Speaks WinDbg, not English

"Possible deadlock among 2 threads holding contended locks" is accurate but hard to act on. Findings name addresses (0x25a4040a4a8) instead of the code and requests involved.

02

Stack groups show runtime noise

Groups are labelled .InlinedCallFrame and .DebuggerU2MCatchHandlerFrame, which are runtime frames, not the user code that matters.

03

The canvas is mostly empty

About 70% of the window is blank grid, while findings are squeezed into a 280px rail. The hierarchy runs backwards.

04

Nothing links to anything

Clicking a thread in the graph doesn't open its stack. A finding can't take you to the lock, and you can't reach an object's fields or see what's keeping it alive.

05

No start or progress state

There are no recent dumps, no sense of what the analyzer is doing on a 20 GB file, and no route to a sample dump.

06

Narrow diagnosis surface

Deadlocks and heap share are covered. Thread-pool starvation, sync-over-async, exception storms and leak-vs-baseline, which are the common on-call causes, aren't.

Design principles

P1

Verdict → evidence → raw

Every screen reads top-down in three layers: a sentence a non-expert can act on, the structured evidence behind it, then raw ClrMD detail (addresses, MTs, frames) collapsed but always present.

P2

Everything is an entity, every entity is a link

Threads ◆, objects ●, locks ▲, types and requests render as one thr#47 chip style. Clicking a chip opens it in the inspector, and nothing is a dead-end string.

P3

Name things the way the app does

Lead with POST /api/orders/checkout, OrderLedger._gate and CheckoutService.Commit(), not OS thread IDs and hex. Addresses are secondary text.

P4

Teach in place

Jargon such as sync block or GC root carries a hover definition. Each finding includes "What this means" and "What to do next". No AI is needed because the analyzers carry the explanation.

P5

Calm density

Dark, dense, keyboard-first, like a pro tool, but with color reserved strictly for meaning: severity, selection and the accent. If everything is red, nothing is.

P6

Fast or honest about it

Triage-level findings arrive within seconds and deeper analyzers stream in after. Long work shows named stages, never a bare spinner.

Information architecture

Seven places, one inspector, one graph of entities.

Navigation is a fixed left rail of views. Selecting any entity anywhere opens it in a shared right-hand inspector instead of navigating away, with back/forward history (Alt+←). Ctrl+K jumps to anything by name, address, type or route.

Entity model and cross-links

Every entity has a stable URI inside the app (thread/47, object/0x25a4040a4a8, type/System.Byte[], finding/lock.cycle.1). URIs back the inspector history, pins/notes, and report links, and later could back deep links if those come back into scope.

Design system

Dark, dense, and color only where it means something.

Tokens live as CSS custom properties in the React app (tokens.css), mirrored as a TS object for canvas and graph rendering. The neutral ramp is cool and slightly blue. Teal is kept from v1 as the single brand accent, used for selection, focus and primary actions, and never for status.

What were you seeing?
Critical

Deadlock between checkout and inventory reservation

Lock-order inversion on 2 locks · 2 threads in cycle · 31 threads waiting behind
High confidence
What this means

Two pieces of code take the same two locks in opposite order. Under load they eventually interleave: each grabs its first lock, then waits forever for the other's. The process won't recover without a restart.

Evidence
thr#47 POST /checkoutthr#52 POST /inventory/reservelockOrderLedger._gatelockInventoryCache._sync
What to do next
  1. Restart the app pool to recover now.
  2. Make both paths take the locks in one order: _gate before _sync. The inversion is in InventoryService.Reserve() line ~118.
  3. Or drop the nested lock: CheckoutService.Commit() doesn't need _sync while holding _gate.
Warning

Thread pool starved: all 48 workers busy, 212 work items queued

Consequence of the deadlock above, made worse by sync-over-async in 9 threads
High confidence
What this means

New requests can't get a thread, so even endpoints unrelated to checkout time out. The pool grows slowly, about one thread per 500 ms.

What to do next
  1. Fix the deadlock first.
  2. Replace .Result in PricingClient.GetQuote() with await.
Warning

Sync-over-async: 9 threads block on Task.Result

All in PricingClient.GetQuote → HttpClient.SendAsync
Medium confidence

Roadmap

Nine phases. Engine first, then views, then reach.

The worker processes and ClrMD analyzers are the valuable, proven part, and they stay. What changes is the contract (query-style, entity-addressed, explanation-carrying) and everything above it. Each phase ends shippable. The full version with acceptance criteria is in docs/redesign/ROADMAP.md.

Risks & open questions

Bridge chattiness

A 4M-object heap must not cross WebView2 as JSON. Mitigation: the worker paginates and aggregates, the UI only asks for what's on screen, and the treemap gets pre-bucketed data.

GC-root path cost

Full root search on large heaps is slow. Mitigation: BFS with a depth cap, cancellation, a cached reverse-reference index built lazily on first request.

"Plain English" accuracy

Authored explanations must not overclaim. Each finding carries confidence, and the text is templated from evidence, never free-form.

Line numbers

Mockups show InventoryService.cs:118, which needs PDBs. Fall back to method + IL offset when symbols are missing, and make symbol paths a setting.
